# Agent Tab and Engine Rename Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Rename the summarising program from "engine" to "agent" across the app, give it its own tab in the main window, and prompt from the Overview when none is configured.

**Architecture:** A mechanical rename done in two atomic passes, Rust then frontend, because a partial rename does not compile. Then the structural work: `EngineSettings.tsx` splits into an Agent tab and an Application group, a fourth tab is added, and the Overview grows a prompt. One `#[serde(alias)]` carries existing configuration across the rename.

**Tech Stack:** Rust with serde and chrono, Tauri 2, React 19, TypeScript, Vitest with jsdom and Testing Library.

**Spec:** `docs/superpowers/specs/2026-09-01-agent-tab-design.md`

## Global Constraints

- Australian English in all prose, comments and UI copy. NEVER an em-dash (U+2014) anywhere, including commit messages. A git hook blocks them and the commit will fail. Use a comma, colon, parentheses, or two sentences.
- The user-facing word is **"Agent"**, never "AI Agent". Code identifiers are `agent`, `Agent`, `AgentError`, `no_agent`.
- MCP callers are **"clients"**, never "agents", so the word is not overloaded.
- **Two things keep the old name deliberately**, both persisted in the user's capture folder: the ledger's `engine` field, and the ledger `action` string `"engine_test"`. Both get a comment saying why. A test at `src-tauri/src/lib.rs` asserts `"engine_test"`; it must keep passing unchanged.
- No `@testing-library/jest-dom`. Plain vitest matchers: `expect((el as HTMLButtonElement).disabled).toBe(true)`, `expect(el.textContent).toContain(...)`, `toBeTruthy()`. Do not add the dependency.
- Tauri is mocked through `src/test/tauri-mock.ts`. `mockInvoke` installs a handler and an unnamed command throws, so every test names the commands it expects. Note a `void`ed call site turns that throw into an unhandled rejection rather than a failure, so check vitest's output for "Unhandled Errors" as well as the pass count.
- `src/setup.css` and `src/main-window.css` share one namespace, `main-window.css` is imported first, so setup.css wins at equal specificity. `src/test/css-cascade.test.ts` guards identical selectors across both files. It cannot see different selectors matching the same element.
- CI runs, in order: `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, `cargo test`, `npm run build`. All must pass before any commit.

### Task 1: Rename the Rust side, and carry existing configuration across

The rename must be atomic: a half-renamed crate does not compile. Do the whole Rust side in one pass, then make the migration test pass.

**Files:**
- Rename: `src-tauri/src/engine.rs` to `src-tauri/src/agent.rs`
- Modify: `src-tauri/src/{lib,settings,control,ipc,jobs,propose}.rs`

**Interfaces:**
- Consumes: nothing.
- Produces: `settings::Agent` (was `settings::Engine`); `Settings.agent: Option<Agent>`; commands `agent_detect`, `agent_test`, `agent_auth`, `refresh_agent_env`; `agent::AgentError`, `agent::AuthState`, `agent::BUSY_MESSAGE`; error code `"no_agent"`.

- [ ] **Step 1: Write the failing migration test**

This is the most important test in the plan. Without it the rename silently discards an existing configuration. Add to the `#[cfg(test)] mod tests` block at the bottom of `src-tauri/src/settings.rs`:

```rust
    #[test]
    fn settings_written_with_the_old_engine_key_still_load() {
        // Settings carries serde(default), so an unknown key is ignored and a
        // missing one takes its default. Without the alias this parses to
        // agent: None and the user silently loses their configuration.
        let raw = r#"{
            "engine": {
                "label": "Claude Code",
                "command": "/usr/local/bin/claude",
                "args": ["--print"],
                "timeout_secs": 300
            }
        }"#;
        let loaded: Settings = serde_json::from_str(raw).expect("parses");
        let agent = loaded.agent.expect("the old key populates the new field");
        assert_eq!(agent.label, "Claude Code");
        assert_eq!(agent.command, "/usr/local/bin/claude");
    }

    #[test]
    fn settings_are_written_with_the_new_key() {
        let mut settings = Settings::default();
        settings.agent = Some(Agent {
            label: "Codex".to_string(),
            command: "/usr/bin/codex".to_string(),
            args: vec![],
            timeout_secs: 300,
        });
        let json = serde_json::to_string(&settings).expect("serialises");
        assert!(json.contains("\"agent\""), "writes the new key");
        assert!(!json.contains("\"engine\""), "does not write the old one");
    }
```

- [ ] **Step 4: Add the alias that carries old configuration**

In `src-tauri/src/settings.rs`:

```rust
    /// None means no agent connected, which is the shipped state and leaves
    /// the app a pure recorder.
    ///
    /// The alias is a migration. This field was called "engine", and Settings
    /// carries serde(default), so without it an existing settings.json would
    /// parse to None and silently drop the user's agent. Deserialisation
    /// takes either key, serialisation writes this one, and the file
    /// normalises on the next save.
    #[serde(alias = "engine")]
    pub agent: Option<Agent>,
```

```tsx
import { useCallback, useEffect, useState } from "react";
import { invoke } from "@tauri-apps/api/core";
import type { Settings } from "../lib/days";

/// Preferences about the application itself rather than about what it
/// records or how it summarises. One toggle today; it is where a second
/// would go, and it is why launch at login is not in the Recording group,
/// whose own note says it changes what is recorded.
export function AppSettings() {
  const [settings, setSettings] = useState<Settings | null>(null);

  const readSettings = useCallback(async () => {
    setSettings(await invoke<Settings>("get_settings"));
  }, []);

  useEffect(() => {
    void readSettings();
  }, [readSettings]);

  if (!settings) return null;

  return (
    <fieldset>
      <legend>Application</legend>
      <label className="schedule-row">
        <input
          type="checkbox"
          checked={settings.launch_at_login}
          onChange={(event) =>
            void invoke("set_launch_at_login", { enabled: event.target.checked })
              .then(readSettings)
              .catch(() => undefined)
          }
        />
        Ambient Context opens when you log in
      </label>
      <p className="settings-note">
        The app starts with the Mac so the daily summary runs whether or not
        you opened it.
      </p>
    </fieldset>
  );
}
```
